# Задание: прототип АИС «Лизинг» на моковых данных

Ты — опытный full-stack разработчик. Нужно построить **работающий кликабельный прототип** информационной системы лизинговой компании (Казахстан). Не макет, не картинки — приложение, которое реально запускается, хранит состояние, пересчитывает цифры и проводит сделку от заявки до закрытия договора.

Прототип нужен для демонстрации заказчику и проверки бизнес-логики. Реальных интеграций нет — вместо них моки. Авторизация упрощённая. Но бизнес-логика (расчёты, статусы, права, аудит) должна быть настоящей.

---

## 1. Технологический стек

Используй ровно это, без обсуждений:

- **Next.js 15 (App Router) + TypeScript** — единое приложение, фронт и API в одном проекте.
- **Prisma + SQLite** — файловая БД `./prisma/dev.db`, чтобы запускалось одной командой без Docker.
- **Tailwind CSS + shadcn/ui** — UI-компоненты.
- **zod** — валидация на входе API и форм.
- **decimal.js** — ВСЕ денежные вычисления. Нигде не использовать `number` для денег.
- **date-fns** — даты.
- **recharts** — графики на дашбордах.
- **vitest** — юнит-тесты расчётного ядра.

Структура:

```
/app            — страницы и route handlers
/lib
  /calc         — расчётное ядро (чистые функции, без БД)
  /rules        — скоринг, стоп-факторы, лимиты
  /workflow     — движок маршрутов согласования
  /audit        — журнал действий
  /docs         — генерация документов из шаблонов
/prisma
  schema.prisma
  seed.ts       — генерация моковых данных
/components
/tests
```

Запуск должен работать так и только так:

```bash
npm install
npm run db:reset    # миграции + сид
npm run dev
```

## 4. Расчётное ядро (`/lib/calc`) — самая важная часть

Чистые функции без обращения к БД. Покрыть тестами. Вся система обязана пользоваться **только** ими — ни в UI, ни в генерации документов не должно быть дублирующих формул.

```ts
calculateSchedule(input: ScheduleInput): ScheduleLine[]
```

Вход: `assetCost, downPayment, financedAmount, termMonths, annualRate, commission, commissionType (UPFRONT|IN_SCHEDULE), vatRate, residualValue, frequency (MONTHLY|QUARTERLY), firstPaymentDate, scheduleType (ANNUITY|DIFFERENTIATED|CUSTOM), customLines?`

Выход: строки графика с полями `seq, dueDate, principal, interest, vat, commission, total, balance`.

Требования:
- Аннуитет: классическая формула, последний платёж выравнивает остаток в ноль до копейки.
- Дифференцированный: равный основной долг, убывающие проценты.
- Индивидуальный: суммы приходят извне, функция только валидирует, что сумма основного долга равна финансируемой.
- Проценты считать по фактическому количеству дней между датами платежей, база 365.
- Округление до 2 знаков, накопленная разница уходит в последний платёж. `sum(principal) === financedAmount` строго.
- НДС начисляется по конфигурируемому правилу (по умолчанию 12% на вознаграждение и комиссию).
- Остаточная стоимость гасится последним платежом.

```ts
calculateProfitability(lines, financedAmount): { irr, totalPayments, totalInterest, overpayment }
```
IRR считать методом Ньютона с фолбэком на бисекцию.

```ts
allocatePayment(amount, openLines, priority): PaymentAllocation[]
```
Порядок погашения настраивается (по умолчанию: пеня → комиссия → НДС → вознаграждение → основной долг). Частичные платежи поддерживаются. Переплата уходит в аванс следующего периода.

```ts
calculateDpd(lines, asOfDate): { dpd, bucket, principalOverdue, interestOverdue }
```
Бакеты: 1–7, 8–30, 31–60, 61–90, 91–180, 180+.

```ts
recalculateOnRestructuring(contract, changes): PaymentSchedule
```
Старая версия графика **никогда не удаляется**, создаётся новая версия с флагом активности.

## 5. Конфигурируемые правила (`/lib/rules`)

Всё редактируется через админку без изменения кода.

**Скоринг.** Таблица показателей с весами (из ТЗ: финансовое состояние 25%, долговая нагрузка 15%, платёжная дисциплина 15%, отрасль 10%, качество предмета 10%, ликвидность 10%, аванс 5%, срок бизнеса 5%, доп. обеспечение 5%). Для каждого показателя — шкала перевода значения в баллы 0–100. Итог — взвешенная сумма и маппинг в рейтинг A–F по настраиваемым границам. При каждом пересчёте писать запись в `RatingHistory`, старое не затирать.

**Коэффициенты.** Формулы хранятся строками и вычисляются безопасным парсером выражений над статьями отчётности (написать мини-интерпретатор, `eval` запрещён). Набор по умолчанию: Debt/EBITDA, Net Debt/EBITDA, Debt/Equity, DSCR, ROA, ROE, ROS, EBITDA Margin, оборачиваемость ДЗ/КЗ/запасов.

**Стоп-факторы.** Справочник с условиями в том же синтаксисе. HARD блокирует переход заявки дальше вообще. SOFT требует явного оверрайда пользователем с ролью ROLE-05 и обязательным комментарием — оверрайд пишется в аудит.

**Лимиты.** Перед одобрением считать `текущая экспозиция + новая сделка = прогнозная`. Превышение по клиенту, группе или отрасли блокирует стандартный маршрут и включает расширенный.

## 6. Движок согласования (`/lib/workflow`)

Маршрут выбирается по условиям: сумма, продукт, превышение лимита, тип клиента, наличие исключений. Шаблоны маршрутов редактируются в админке: добавить/убрать/переставить шаг, задать роль и SLA в часах.

Базовый маршрут: Менеджер → Аналитик → Маркетинговое заключение → Юрист → Риски → ПОД/ФТ → Комитет.

Требования:
- Maker-Checker: пользователь, создавший объект, не может сам его согласовать.
- SLA: у шага есть дедлайн, при приближении (80% времени) уведомление исполнителю, при нарушении — эскалация руководителю. Считать в рабочих часах по производственному календарю (сделать простой справочник выходных РК).
- Возврат на доработку с обязательным комментарием.
- Каждый переход пишется в `ApplicationStatusHistory` и в аудит.

Статусы заявки: `DRAFT → REGISTERED → DOCUMENTS → ANALYSIS → RISK → APPROVAL → COMMITTEE → APPROVED|REJECTED → CONTRACT → FUNDED`.

## 7. Экраны

**Общие.** Слева меню по модулям, отфильтрованное по правам роли. Сверху — глобальный поиск (по ИИН, БИН, ФИО, наименованию, номеру заявки, номеру договора, VIN, госномеру, серийному номеру), переключатель роли, колокольчик уведомлений.

**Дашборд «Мои задачи».** Что висит на текущей роли, с подсветкой просроченных SLA.

**Клиенты.** Список с фильтрами, карточка клиента с вкладками: Общее, Связанные лица, Досье, Заявки, Договоры, Финансы, Рейтинг, ПОД/ФТ, EWS. При вводе БИН — проверка дублей с предупреждением.

**Заявки.** Список, карточка с шагами процесса в виде степпера, встроенный калькулятор, вкладки Документы, Финанализ, Риски, Согласование, Комитет.

**Калькулятор.** Отдельная страница, пересчёт мгновенно при изменении любого параметра, таблица графика, график «основной долг / вознаграждение» по периодам, показатели доходности. Кнопка «Сохранить в заявку».

**Кредитный комитет.** Повестка на дату, по каждой заявке пакет материалов одной страницей, голосование (за/против/воздержался), подсчёт кворума, автоматическая генерация протокола.

**Договоры.** Карточка договора: реквизиты, активный график с историей версий, предметы лизинга, страховки, платежи, начисления, ковенанты, мониторинг, документы.

**Платежи.** Реестр поступлений, кнопка «Загрузить банковскую выписку» (парсинг CSV из моков), ручная и автоматическая разноска с показом, как именно разложилась сумма.

**Просрочка.** Реестр с DPD и бакетами, карточка работы с должником, история контактов, обещания платежа.

**Мониторинг.** Список плановых проверок, форма результата с загрузкой фото (плейсхолдеры), оценка состояния.

**Дашборды BI.** Четыре вкладки: Руководство (портфель, продажи, доход, план/факт, просрочка), Риски (портфель по рейтингам, DPD, PAR30, PAR90, концентрации, EWS, ковенанты), Продажи (заявки, конверсия, отказы, средний чек, время рассмотрения), Казначейство (ожидаемые поступления, денежный поток).

**Администрирование.** Матрица прав, маршруты согласования, скоринговая модель, стоп-факторы, лимиты, формулы коэффициентов, шаблоны документов, справочники, настройки уведомлений.

**Журнал аудита.** Только чтение, фильтры по пользователю, объекту, периоду, операции. Показывать старое и новое значение. Возможности удаления записей не существует ни в UI, ни в API.

**Личный кабинет клиента.** Отдельный упрощённый интерфейс для ROLE-18: договор, график, задолженность, ближайший платёж, документы, уведомления, подача заявления на досрочный выкуп и реструктуризацию.

## 8. Документы

Шаблоны хранить как HTML с плейсхолдерами `{{client.name}}`, `{{contract.number}}`, `{{schedule.table}}` и т.п. Редактируются в админке. Генерация — подстановка данных и вывод в PDF через печать браузера.

Набор: договор финансового лизинга, график платежей, договор купли-продажи, акт приёма-передачи, договор залога, договор гарантии, дополнительное соглашение, протокол комитета.

Повторный ручной ввод уже известных системе данных при генерации запрещён — всё тянется из карточки сделки.

**Мок ЭЦП.** Кнопка «Подписать ЭЦП» открывает модалку с выбором фиктивного сертификата, после подтверждения фиксируются подписант, время, «отпечаток» сертификата и SHA-256 хеш содержимого документа. При любом последующем изменении документа система показывает, что подпись нарушена.

## 9. Моковые данные (`prisma/seed.ts`)

Данные должны выглядеть правдоподобно для Казахстана и покрывать все состояния системы.

- **40 клиентов**: ТОО, АО, ИП, физлица. Реалистичные названия («ТОО АгроТехСервис», «ТОО КазСтройМонтаж»), валидные по контрольной сумме БИН/ИИН, ОКЭД, адреса в Алматы, Астане, Шымкенте, Караганде. 3 группы связанных компаний.
- **15 поставщиков**: автодилеры, поставщики спецтехники и оборудования.
- **60 заявок** во всех статусах: черновики, на анализе, на согласовании, в комитете, одобренные, отказанные.
- **35 договоров** с разными сроками (12–60 месяцев), суммами (от 5 млн до 800 млн тенге), ставками (16–24%), типами графиков. Даты выдачи распределить за последние 3 года.
- **Предметы лизинга**: грузовики, седельные тягачи, экскаваторы, автобусы, станки, медицинское оборудование. С VIN, госномерами, серийными номерами.
- **Платежи за всю историю** договоров, с разными сценариями: платят вовремя, платят частями, платят с опозданием, перестали платить.
- **Просрочка** во всех бакетах, включая 2 договора со 180+ и начатым изъятием.
- **Финансовая отчётность** за 3 периода по каждому корпоративному клиенту, с осмысленными цифрами, из которых коэффициенты считаются в разумные значения.
- **Рейтинги** с историей изменений, клиенты всех цветов EWS.
- **Страховки**: часть действующие, часть истекают в ближайшие 30 дней (чтобы сработали напоминания), часть просрочены.
- **Ковенанты**: выполненные, нарушенные, ожидающие проверки.
- **Записи мониторинга** и **аудит** за весь период.

Сид должен быть детерминированным (фиксированный seed генератора), чтобы демо каждый раз выглядело одинаково.

Отдельно положить файл `/mocks/bank-statement.csv` — банковскую выписку для демонстрации загрузки и автоматической разноски.

## 10. Моки интеграций

Сделать `/lib/integrations` с реализациями-заглушками и единым интерфейсом, чтобы потом подменить на реальные:

- **1С**: две кнопки — «Выгрузить в 1С» и «Загрузить из 1С», генерируют и принимают JSON, пишут лог обмена.
- **Банк**: импорт CSV-выписки.
- **Кредитное бюро**: кнопка «Запросить отчёт», через 2 секунды возвращает сгенерированный отчёт с историей займов. Каждый запрос журналируется.
- **Госисточники**: «Проверить по БИН» — возвращает статус регистрации, налоговую задолженность, участие в судах, наличие в реестрах.
- **Уведомления**: канал вместо реальной отправки пишет в таблицу и показывает в интерфейсе «Исходящие уведомления».

Все моки отдают ответ с задержкой 0.5–2 секунды, чтобы интерфейс честно показывал состояния загрузки.

## 11. Сквозной сценарий, который обязан работать

После `npm run db:reset && npm run dev` должно быть возможно без единой ошибки пройти:

1. Войти менеджером, создать нового клиента, получить предупреждение о дубле при вводе существующего БИН.
2. Создать заявку, посчитать график в калькуляторе, приложить документы, отправить на рассмотрение.
3. Переключиться на аналитика, ввести отчётность, увидеть автоматически посчитанные коэффициенты.
4. Переключиться на риск-менеджера, увидеть скоринг и рейтинг, поймать сработавший мягкий стоп-фактор, получить оверрайд у руководителя рисков.
5. Пройти согласование по маршруту, увидеть, как тикает SLA.
6. Вынести на комитет, проголосовать разными членами, получить решение и автоматический протокол.
7. Сформировать договор из шаблона, подписать мок-ЭЦП.
8. Завести предмет лизинга и страховку, зафиксировать передачу.
9. Загрузить банковскую выписку, увидеть автоматическую разноску платежей по графику.
10. Промотать дату вперёд (кнопка «Симулировать время» в админке), увидеть возникшую просрочку, автоматически созданную задачу взыскателю и покраснение клиента в EWS.
11. Провести реструктуризацию, увидеть новую версию графика и сохранённую старую.
12. Открыть дашборды и убедиться, что цифры изменились.
13. Открыть журнал аудита и найти там все совершённые действия с прежними и новыми значениями.

Кнопка «Симулировать время» — обязательна. Она сдвигает системную дату приложения, чтобы на демо показывать просрочку, истечение страховок и срабатывание ковенантов.

## 12. Требования к качеству

- TypeScript в строгом режиме, `any` запрещён.
- Все суммы — `Decimal`, сравнение денег через методы decimal.js.
- Валидация zod на каждом API-роуте.
- Каждое изменяющее действие пишет в аудит через единый хелпер, а не вручную в каждом месте.
- Проверка прав — через мидлвар, а не копипастой в обработчиках.
- Тесты обязательны для: расчёта всех типов графиков, IRR, разноски платежей, расчёта DPD, скоринга, интерпретатора формул. Минимум 40 тестов, все зелёные.
- Интерфейс на русском языке. Формат чисел — разделение разрядов пробелом, валюта «₸».
- Мобильную адаптивность не делать, кроме личного кабинета клиента.
- README с описанием запуска, списком тестовых пользователей и пошаговым сценарием демонстрации из раздела 11.

## 13. Порядок работы

Делай последовательно, коммить после каждого пункта, после каждого пункта приложение должно запускаться:

1. Каркас проекта, схема Prisma, миграции, пустой сид.
2. Расчётное ядро с тестами. **Пока тесты не зелёные, дальше не идти.**
3. Аутентификация-заглушка, роли, матрица прав, аудит.
4. Справочники: клиенты, поставщики, предметы, документы.
5. Заявки, калькулятор в интерфейсе.
6. Финанализ, коэффициенты, скоринг, стоп-факторы, лимиты.
7. Движок маршрутов, SLA, уведомления.
8. Комитет, протокол.
9. Договоры, шаблоны документов, мок-ЭЦП.
10. Платежи, разноска, просрочка, взыскание.
11. Страхование, ковенанты, мониторинг, EWS, реструктуризация, изъятие.
12. Дашборды BI, глобальный поиск.
13. Личный кабинет клиента.
14. Моки интеграций.
15. Полный сид данных, прогон сценария из раздела 11, README.

Если какое-то требование противоречит другому или недостаточно определено — принимай решение сам, делай разумное допущение и фиксируй его в файле `ASSUMPTIONS.md`. Не останавливайся, чтобы задать вопрос.
