# Как провести показ: подготовка, структура, слова ведущего

Этот файл — руководство ведущего. Сами слайды и заметки к ним — в [slides/](slides/README.md); технический маршрут и критерии приёмки — в [DEMO_SCENARIO.md](DEMO_SCENARIO.md); ограничения — в [../ASSUMPTIONS.md](../ASSUMPTIONS.md).

Формат, на который рассчитан материал: 20 минут — 5 минут слайдов, 11–12 минут живого показа, 3–4 минуты вопросов. Один ведущий, ноутбук, Chromium, локальный сервер, интернет не нужен.

---

## 0. Главное правило

Это **прототип на синтетических данных**. AML, ЭЦП и банковская выписка — обозначенные имитации. Ни одна цифра в демо не является утверждением о действующих налоговых правилах или о фактической экономии времени. Если прозвучит вопрос «это уже работает с банком?» — ответ «нет, это имитация, реальная интеграция в объём прототипа не входила».

Нарушение этого правила обесценит весь показ быстрее, чем любая техническая ошибка.

## 1. Подготовка (за 30 минут до показа)

```bash
cd leasing-demo
npm ci
npm run db:setup        # создаст и засеет prisma/dev.db, существующие данные не тронет
npm run build
npm start               # http://127.0.0.1:3000
```

Чек-лист перед аудиторией:

- [ ] В шапке видна системная дата **21.09.2026**. Если нет — база не в исходном состоянии, сделать сброс (см. ниже).
- [ ] Выбрана роль **Айдар Сатпаев — Менеджер по продажам**.
- [ ] Открыта одна вкладка, масштаб 100%, ширина окна не меньше ~1440 px.
- [ ] Закрыты уведомления ОС, мессенджеры, почта.
- [ ] Рядом открыт этот файл или распечатан раздел 3.
- [ ] Прогнан «сухой» проход сценария целиком — минимум один раз, накануне.

**Сброс к исходному состоянию** (удаляет содержимое локальной демо-базы; если нужны результаты прошлого прогона — сначала скопировать `prisma/dev.db`):

```bash
npm run db:reset -- --confirm-demo-reset
npm start
```

После сброса старые вкладки со случайными ID дают 404 — вернуться на главную и выбрать роль заново.

## 2. Слайды (5 минут, 6 слайдов)

Слайды нужны только чтобы задать рамку. Всё содержательное — в живом показе, не пересказывайте его на слайдах.

**Слайд 1. Название.**
«АИС Лизинг — прототип рабочего места». Подзаголовок: «Демонстрация процесса, синтетические данные». Дата, имя ведущего.

**Слайд 2. Проблема (одна фраза, без цифр).**
Сделка живёт в почте и таблицах: непонятно, у кого она сейчас, на каком основании принято решение и сколько клиент должен на сегодня.

**Слайд 3. Что показываем.**
Одна сделка от расчёта до оплаты, три сценария:
1. Досье и заявка
2. Согласование и договор
3. Платёж и просрочка

**Слайд 4. Схема процесса.**
Заявка → 5 последовательных согласований (аналитик, руководитель продаж, юрист, риск-менеджер, ПОД/ФТ) → кредитный комитет (2 голоса из 3) → договор и график → платежи → просрочка.
Скажите вслух: правило «2 из 3» — демонстрационное, реальный регламент комитета не согласован.

**Слайд 5. Что настоящее, а что имитация.** Самый важный слайд.

| Настоящее в прототипе | Имитация |
|---|---|
| Последовательный маршрут и запрет перескока | AML / ПОД-ФТ проверки |
| Расчёт графика, аннуитет, IRR (decimal.js) | ЭЦП (НУЦ РК) |
| Транзакционное создание договора и графика | Банковская выписка (читается подготовленный CSV) |
| Распределение платежей по приоритету, защита от переплат и дублей | Документооборот (DMS) |
| Просрочка с учётом частичных оплат, аудит действий | Аутентификация и разграничение доступа |

**Слайд 6. Границы.**
Нет production-входа, нет изоляции клиентских данных, нет сертификации расчётов. Открытый переключатель ролей — приём показа, а не модель безопасности. SQLite и локальный запуск рассчитаны только на этот показ.

После слайда 6 — сразу в приложение, не задерживайтесь.

## 3. Живой показ (11–12 минут)

Формула каждого блока: **кто я → что делаю → что должно появиться на экране**. Проговаривайте роль вслух при каждом переключении — иначе аудитория теряет нить.

### Блок 1. Досье и заявка — 2 минуты
**Роль: Айдар Сатпаев — Менеджер по продажам**

1. «Клиенты» → найти «ДЕМО» → открыть **ТОО ДЕМО — Учебная логистика**.
   Сказать: «Досье учебное, БИН фиктивный. Здесь видно рейтинг, финансовые показатели и историю проверок».
2. «Заявки» → «Новая заявка». Заполнить: клиент — Учебная логистика, продукт — грузовой транспорт, **60 000 000 / 12 000 000 / 12 месяцев / 18%**, аннуитет. Создать.
3. Показать на карточке: номер заявки, **финансирование 48 000 000 ₸**, график из 12 строк, **IRR 23.91%**, скоринг **76.25 / рейтинг B**, 0 стоп-факторов, маршрут **STD**.
   Сказать: «График и оценка риска посчитаны при создании, не введены руками».
4. Нажать **«Отправить на рассмотрение»**.
   Ожидаемо: появляется маршрут согласования, активен ровно один шаг — «Анализ кредитной заявки», остальные «Ожидает предыдущий шаг».
   Сказать: «Ключевая вещь: активен один шаг. Перескочить нельзя».

*Если время поджимает* — пропустите создание и работайте с готовым черновиком `Z-DEMO-001`, прямо сказав, что это подготовленные данные.

### Блок 2. Согласование и договор — 5–6 минут

Переключение роли сохраняет текущий адрес, поэтому карточка заявки остаётся открытой.

Последовательно, каждый раз нажимая **«Согласовать»**:

| # | Роль | Пользователь |
|---|---|---|
| 1 | Кредитный аналитик | Динара Ахметова |
| 2 | Руководитель продаж | Марат Жумабаев |
| 3 | Юрист | Зауреш Бектанова |
| 4 | Риск-менеджер | Алия Нурпеисова |
| 5 | ПОД/ФТ | Нурлан Оспанов |

После каждого шага показывайте пальцем, как подсвечивается следующий. На 2–3-м шаге можно ускориться — идея уже понятна.

Сказать один раз: «Стоп-факторы проверяются на каждом решении. HARD блокирует сделку без вариантов, SOFT требует письменного обоснования от руководителя рисков. У этой небольшой учебной заявки маршрут стандартный».

**Комитет.** Роль **Дамир Султанов (член кредитного комитета)** → ссылка «Перейти к голосованию» → найти свой номер заявки → **«За»**.
Ожидаемо: заявка **не одобрена**, ваш голос отмечен.
Сказать: «Одного голоса мало — это и есть смысл коллегиального решения».

Роль **Тимур Карибаев** → **«За»** в той же строке.
Ожидаемо: заявка становится одобренной и уходит из текущей повестки.
Сказать: «Правило "2 из 3" — демонстрационное».

**Договор.** Роль **Арман Тлеубаев — Лизинговые операции** → «Договоры» → создание → выбрать свою одобренную заявку → **«Сформировать договор»**.
Ожидаемо: карточка договора ДЛ-2026-…, график 12 строк, предмет лизинга, статус «Действует», просрочки нет.
Сказать: «Договор, график и предмет создаются одной транзакцией — половинчатого состояния не бывает».

Можно нажать **«Подписать ЭЦП»**, обязательно с оговоркой: «Это имитация. В продукте здесь интеграция с НУЦ РК, сейчас фиксируется только запись аудита».

### Блок 3. Платёж и просрочка — 3–4 минуты
**Роль: Куаныш Сериков — Бухгалтерия**

1. «Договоры» → открыть **ДЛ-DEMO-001** (подготовленный договор с историей платежей — скажите это прямо).
   Показать красный баннер: **«Просрочка: DPD 31 · 31–60 дней»**.
2. В блоке «Принять платёж» внести **1 000** → «Зачислить».
   Ожидаемо: уведомление «Платёж зачислен», поле очищено, в графике первая строка получила оплату.
   Сказать: «Распределение идёт по приоритету: пени → комиссия → НДС → проценты → основной долг, с учётом ранее внесённых сумм».
3. «Платежи» → **«Импортировать демо-выписку»**.
   Ожидаемо: **импортировано 2**, 25 000 ₸, именно по ДЛ-DEMO-001.
   Сказать: «Это чтение подготовленного CSV, а не подключение к банку. Строка зачисляется только при точном совпадении номера договора и валюты».
4. Нажать **ту же кнопку ещё раз**.
   Ожидаемо: **импортировано 0, ранее учтено 2**.
   Сказать: «Повторная загрузка того же файла не задваивает платежи». Это самый убедительный момент показа для финансистов — не проскакивайте его.
5. Вернуться в договор: первая строка графика — **оплачено 26 000 ₸, статус PARTIAL**, договор остаётся в просрочке.
   Сказать: «Частично оплаченный период не исчезает из просрочки — это частая ошибка учёта».
   *Колонка «Статус» может уйти за правый край: таблица прокручивается по горизонтали, либо опирайтесь на баннер сверху.*

**Время.** Роль **Руслан Айтмуханов — Системный администратор** → «Администрирование» → сдвиг времени **+30 дней** → «Симулировать время».
Вернуться в ДЛ-DEMO-001.
Ожидаемо: системная дата **21.10.2026**, баннер **«Просрочка: DPD 61 · 61–90 дней»**.
Сказать: «61 день — это не случайное число: первый непогашенный период приходится на 21.08.2026, внесённых 26 000 ₸ не хватает на платёж 75 371,61 ₸, поэтому просрочка считается от 21 августа».

**Финал.** «Аудит» — показать записи: создание заявки, согласования, решение комитета, платежи.
Закрывающая фраза: «Сотрудник видит одну сделку целиком: у кого она сейчас, на каком основании принято решение и сколько клиент должен на сегодняшнюю дату».

## 4. Если что-то пошло не так

| Симптом | Что делать |
|---|---|
| Страница отдала 404 после сброса базы | Вернуться на главную, выбрать роль заново — ID объектов пересоздались |
| Кнопки «Согласовать» нет | Выбрана не та роль, либо шаг уже пройден. Проверьте подсвеченный шаг маршрута |
| Заявка не одобряется после двух голосов | Голосовали одним и тем же пользователем. Нужны два разных члена комитета |
| Импорт дал 0 с первого раза | Выписка уже импортирована в этом прогоне. Так и скажите: «это и есть защита от дублей» |
| DPD не 61 | Сдвиг времени был не на 30 дней или база не в исходном состоянии |
| Сервер не поднялся | **Не выдавайте статичные картинки за работающую систему.** Покажите снимки из `.demo-artifacts/`, скажите, что это записи реального прогона, и признайте, что живое демо не состоялось |

## 5. Ответы на вероятные вопросы

**«Это можно ставить в работу?»** Нет. Нет аутентификации, разграничения доступа клиентских данных и сертификации расчётов. Это прототип процесса.

**«Расчёты правильные?»** Арифметика выполнена аккуратно (decimal.js, фактические дни, база 365), но формулы, НДС 12% и комиссия — учебные параметры. Их нужно подтвердить с владельцем процесса.

**«Сколько времени это экономит?»** Не измерялось. Прототип показывает прослеживаемость, а не эффект.

**«Почему все роли доступны одним переключателем?»** Это приём показа, чтобы за 10 минут пройти маршрут одним человеком. В продукте — обычный вход и права.

**«Данные настоящие?»** Нет, полностью синтетические: БИН `000000000001`, адреса `example.invalid`, телефоны нерабочие.

**«Сколько заняла разработка / что дальше?»** Следующие шаги перечислены в ASSUMPTIONS.md, раздел «После демо»: подтверждение формул и регламента, аутентификация и права, реальные интеграции, тесты конкурентной записи.
